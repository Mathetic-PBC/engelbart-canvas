# Local interface builds

In a workspace document, enter `@bart Can you make a timer using this workspace's context?` and send it. Bart can recognize an interface-building request and propose a build; factual questions and design discussions stay read-only. `--build` remains an optional shortcut that goes straight to planning. Model/effort flags still select the coding agent, for example `@bart --astra --high Make a timer`.

Bart's Claude calls use the signed-in Claude Code subscription. Gateway/API-key overrides are cleared for those processes after login-shell startup, so an inherited proxy cannot override the subscription. This does not edit shell settings, credentials, or the proxy used by other tools and interactive terminals.

Claude prepares a read-only plan first, using the existing app and workspace context. Notifications shows that plan with **Build locally** and **Not now**; Bart's pending reply links to it. There is no system dialog and no build strip above Stage. The coding agent, Git initialization, dependency scripts and app server wait for Build locally. Planning always uses Claude Code (a configured Claude model if selected, otherwise the first Claude ladder model); it requires Claude sign-in. There is no silent provider or hard-coded-plan fallback. Workspace context therefore goes to Claude for planning and to the selected coding agent for execution.

Claude chooses 1–4 specific coding steps and describes the four runtime phases: install, compile, start and verify. Each coding step runs in a separate bounded agent turn against the same app folder. The main process advances a step only after its agent turn/command/browser check finishes, labels unnecessary install/compile steps as skipped, and shows failures rather than fake completions. A launch repair is explicitly reported before retrying the runtime steps. The plan and step outcomes persist with the app. A proposal is not consent: only a one-time, workspace-scoped approval starts execution.

Each workspace owns one local Git repository under `<dataRoot>/.local-apps/<projectId>/<workspaceId>/app`. Further approved build requests update that same folder. Git is initialized locally; Canvas does not create a remote repository, commit, or push. Context is assembled by the existing Bart context reader (workspace, current note, mentioned notes, catalog); a saved link alone does not imply its authenticated contents have been fetched.

The build agent writes the app and `engelbart-preview.json`. Canvas installs dependencies, starts the foreground server on an allocated loopback port, verifies that the listener belongs to its process group, checks the HTML response, and renders the page in an isolated Electron browser before reporting it live. A blank page, raw API response, common framework error page, exited command, stale build recipe, or non-loopback listener does not become a preview. One repair attempt receives the actual failure and recent logs.

The generated manifest uses version 1, kind `interface`, the current `buildId`, a name, relative `cwd`, optional dependency `install` and compilation `build` commands, foreground `command` containing `{port}`, and local `path`. For example, a dependency-free Node app can use `install: null`, `build: null` and `command: "node server.cjs {port}"`. Unchanged dependencies with an existing `node_modules` directory are reused; the `build` command always runs. The server must bind to `127.0.0.1`. Dependencies, Git, Node and any other runtime come from the person's local installation/PATH. There is no global runtime installation or automatic E2B fallback.

The shared notification bell shows local builds alongside repository builds across workspaces. A local notification offers Open, Stop, Restart and Details (plan, logs, folder and launch commands). Read/dismiss state survives renderer reloads; new phases notify without every log line creating another alert. A successful build opens/focuses the app's existing Stage tab only in its requesting workspace. A build finishing elsewhere does not navigate the workspace currently in front; use the notification's Open action when ready. The local repository is attached to Context. Files, recipe, plan and logs survive app restarts; servers do not auto-start. Restart explicitly authorizes running the saved app again, rereads its manifest, and chooses a new port if the old one is occupied.

Stopping, deleting the owning workspace, changing data mode, or quitting stops owned process groups. A process is never killed just because it occupies a port, and persisted PIDs are never trusted. Closing a Stage tab does not stop the server; use Stop. Processes intentionally detached by an app itself are not supported—launch commands must remain foreground. Restart asks in Notifications. Approvals apply only to the current request and are never restored as permission after relaunch; declining an update leaves an existing live app running.

This is local execution, not remote/container isolation. The confirmation explains that commands run with the user's local account and context goes to the selected subscription agent. Credential-like environment variables are stripped. The Codex build route uses a dedicated auth home and `workspace-write`, not full-access/bypass mode, following [OpenAI's non-interactive execution guidance](https://learn.chatgpt.com/docs/non-interactive-mode); context folders are not added as writable roots. Claude gets an explicit tool list with restricted mode and no ambient MCP/settings, with its direct file tools confined to the app folder. Both prompts treat original context files as read-only. Shell commands and dependency scripts still run locally with host access: only approve builds you trust. This is not a claim that the whole app runtime is sandboxed.

Verification: `node --test test/local-preview.test.cjs test/local-build-notifications.test.cjs test/bart.test.cjs test/doc-editor.test.cjs test/right-pane.test.cjs test/sandbox-notifications.test.cjs`; `npm run build`; `electron scripts/smoke-local-preview.cjs`. The smoke test uses disposable app data and scripted proposal/planner/coding agents; process supervision, IPC, renderer, browser verification, and Stage navigation are real. It does not use an actual model subscription or E2B.

Add `--claude` to use Claude for coding too. This test uses the person's signed-in subscriptions and should be run only with permission.
